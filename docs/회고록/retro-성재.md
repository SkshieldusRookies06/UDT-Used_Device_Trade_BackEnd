## 3. 배운 것 — 협업



- **파일 소유권 기반의 작업 분리와 충돌 제로화**: 공용 인프라(`api/client.js`, 전역 스토어, 공용 컴포넌트, 루트 라우트)는 FE-A가 전담하고, 도메인 페이지(`Product*`)와 전용 API(`api/products.js`)는 FE-B가 소유하는 명확한 오너십 분리를 통해 여러 브랜치가 병렬로 진행됨에도 머지 충돌(Merge Conflict) 없이 매끄럽게 협업할 수 있었습니다.
- **계약 우선(Contract-First) 개발과 목 서버 활용**: 백엔드 API 구현 완료를 마냥 기다리지 않고, 사전에 정의된 `SPEC.md`와 `npm run mock` 목 서버를 기반으로 4가지 상태(로딩·정상·빈 결과·에러)를 선행 구현하여 프론트엔드 개발의 병목을 없앴습니다.
- **URL 중심 상태 관리(Single Source of Truth)**: 검색어, 카테고리 필터, 페이지 번호를 전역 스토어 대신 URL 쿼리 파라미터로 일원화하여, 팀원 간 화면 공유나 뒤로가기/새로고침 시에도 동일한 조회 결과가 완벽히 재현되도록 보장했습니다.

## 4. 아쉬운 것 · 다음에 다르게 할 것



백엔드와 프론트엔드 간의 검증 책임 범위를 초기에 명확히 합의하지 못해, 클라이언트에서 임의로 버튼을 비활성화했다가 서버 메시지를 그대로 표출하도록 다시 수정한 점이 아쉬웠습니다.
이미지 업로드 기능 구현 시 첨부 개수 초과나 지원하지 않는 확장자 등 엣지 케이스를 개발 초기에 꼼꼼하게 검토했다면 후속 교정 작업을 줄일 수 있었을 것입니다.
전역 상태(Zustand)로 다룰 항목과 URL 쿼리 파라미터로 동기화할 상태의 기준을 프로젝트 착수 전에 팀원들과 더 깊이 논의했으면 라우팅 설계가 한결 수월했을 것입니다.
다음 프로젝트에서는 API 명세의 요청/응답 필드뿐만 아니라 백엔드 예외 코드(ErrorCode)와 에러 메시지 처리 정책을 첫날 킥오프 회의에서 함께 일치시키는 과정을 반드시 거치겠습니다.
아울러 목 서버와 실서버 간의 미세한 스펙 불일치를 사전에 차단할 수 있도록 스키마 기반 계약 검증(Contract Test)을 초기에 자동화하여 개발 안정성을 높이고 싶습니다.

## 5. 소감 — 발표 1분 원고

백엔드와의 API 계약을 철저히 준수하며 목 서버를 적극 활용하고, URL 기반 상태 동기화와 전역 스토어를 결합해 데이터 정합성을 유지하는 실전 프론트엔드 아키텍처를 깊이 체득했습니다.
