## 3. 배운 것 — 협업

- **API 약속을 먼저 정해 두니 동시에 작업할 수 있었다.**
  - 새 기능이 필요할 때도 명세서와 목 서버를 먼저 고치고 구현을 뒤따르게 했다. 프론트엔드는 백엔드 구현을 기다리지 않고 바로 화면 작업을 진행할 수 있었다.
- **"다 했다"를 말이 아니라 테스트로 확인했다.**
  - 중간 점검에서 고칠 부분을 문서로 전달하는 대신, 실패하는 테스트로 만들어 각 담당자에게 넘겼다. 담당자는 자기 테스트만 통과시키면 됐고, 리뷰할 때도 테스트 결과만 보면 되어 훨씬 수월했다.
- **다른 사람이 맡은 파일은 담당자를 거쳐서 고쳤다.**
  - 팀원이 공통 코드에서 버그를 찾았을 때 직접 고치지 않고 알려 주었고, 같은 원인의 다른 버그까지 함께 고칠 수 있었다. 나도 다른 팀원의 파일은 수정할 내용을 전달하고 담당자가 반영하도록 했다.

## 4. 아쉬운 것 · 다음에 다르게 할 것

프로젝트 기간이 짧아서 명세서와 문서를 미리 많이 준비해 왔고, 덕분에 첫날부터 바로 개발을 시작할 수 있었습니다.
하지만 그만큼 팀원들이 설계 단계에 함께 참여할 기회는 적었던 것 같습니다.
또 문서가 많아지다 보니 같은 내용이 여러 곳에 적혀 있어서, 코드가 바뀔 때마다 문서를 찾아 고치는 데 시간이 많이 들었습니다.
프론트엔드와 백엔드의 연동 점검도 첫 통합 때 꼼꼼히 했다면, 화면에 값이 잘못 나오는 문제를 더 일찍 찾을 수 있었을 것입니다.
다음에는 팀원들과 함께 설계하고, 중요한 내용은 한 곳에만 적고, 통합할 때마다 연동 점검을 반복하는 방식으로 진행하고 싶습니다.

## 5. 소감

저는 팀장을 맡아 API 명세와 공통 코드, 마이페이지·파일 업로드·분쟁 기능을 담당한 윤동호입니다.
짧은 기간에 일곱 명이 동시에 작업해야 했기 때문에, 처음부터 API 약속을 먼저 정하고 목 서버와 자동 검사로 그 약속을 지키게 하는 데 가장 많은 신경을 썼습니다.
덕분에 프론트엔드와 백엔드가 서로를 기다리지 않고 각자 개발을 진행할 수 있었고, 마지막에는 하나의 서비스로 맞출 수 있었습니다.
가장 어려웠던 점은 제 기능을 개발하면서 동시에 팀 전체의 진행 상황과 코드가 명세와 맞는지를 계속 확인하는 일이었습니다.
통합 과정에서 화면에 값이 잘못 나오거나 에러 코드가 다르게 나오는 문제를 하나씩 비교하며 찾아 고치면서, 약속을 문서에 분명하게 적어 두는 것이 얼마나 중요한지 배웠습니다.
또 "다 했다"는 말보다 테스트로 결과를 확인하는 방식이 팀원 모두에게 더 편하고 정확하다는 것도 알게 되었습니다.
다음 프로젝트에서는 설계 단계부터 팀원들과 함께 결정하면서, 이번에 만든 방식을 더 다듬어 보고 싶습니다.
약속을 함께 지켜 주고, 문제가 보이면 먼저 알려 준 팀원들 덕분에 끝까지 올 수 있었습니다. 감사합니다.
