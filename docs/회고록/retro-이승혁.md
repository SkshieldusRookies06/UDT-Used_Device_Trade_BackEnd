## 3. 배운 것 — 협업

- **API 명세서(`SPEC.md`) 기반의 병렬 개발과 목(Mock) 서버 활용:** 프론트엔드와 백엔드가 동시에 작업을 진행할 때 계약(약속)의 중요성을 체감했습니다. 백엔드 API가 완전히 나오기 전에도 `npm run mock`을 통해 합의된 응답 데이터를 바탕으로 화면을 멈춤 없이 개발할 수 있어, 개발 속도와 효율을 크게 높일 수 있었습니다[cite: 4].
- **구현 전 명확한 상태 기획 합의 (with BE-D):** 서비스의 중심인 '거래 상세 화면(T-017)'을 개발하기 전, 백엔드(BE-D) 담당자와 '거래 상태 5종 × 역할(구매/판매자) 2종'에 따른 노출 버튼 표를 사전에 완벽히 합의했습니다[cite: 4]. 코드를 치기 전 기획을 먼저 맞춘 덕분에, 복잡한 상태 분기 로직에서 발생할 수 있는 혼선과 버그를 원천 차단했습니다.
- **프론트엔드 팀 내 공용 파일 규칙 준수 (with FE-A):** `ProductCard`, `StatusBadge` 등 프로젝트의 공통 컴포넌트나 스타일(`*.module.css`)이 변경되어야 할 때, 임의로 내 입맛대로 수정하지 않았습니다[cite: 4]. 대신 1안과 2안을 정리하여 담당자(FE-A)에게 먼저 요청하거나 팀 채널에 선공지함으로써, UI 의존성이 깨지는 충돌을 예방하는 실무 프로세스를 익혔습니다.
- **프로젝트를 보여주는 시연 설계:** 서비스의 존재 이유인 '에스크로(안전 결제)'의 신뢰성을 보여주기 위해, 사용자가 '구매확정' 버튼을 누르는 순간 판매자의 잔액이 증가하는 과정을 화면 하나에 직관적으로 배치했습니다[cite: 4]. 내가 짠 코드가 실제 발표 시연에서 사용자에게 어떤 시각적 가치를 전달하는지 팀 전체의 관점에서 고민해 볼 수 있었습니다.

## 4. 아쉬운 것 · 다음에 다르게 할 것

이번 프로젝트에서 가장 헤맸던 부분은 상품 상세 화면에서 사진 미리보기가 안 떴을 때였습니다. 깃허브를 쓰거나 화면 틀을 잡는 건 오히려 괜찮았는데, 이미지 경로가 꼬여서 화면에 사진이 안 나오는 문제를 고치는 부분이 힘들었습니다. 그리고 가짜 데이터가 아니라 진짜 백엔드 서버를 켜서 API를 연결하고 환경변수(토큰)를 넣는 과정이 저에겐 너무 낯설고 어려웠습니다. 그래도 이 과정들을 겪으면서 프론트엔드와 백엔드가 어떻게 이어지는지 흐름을 조금이나마 이해하게 되었습니다. 다음 프로젝트를 할 때는 코드부터 치기보다 데이터가 오고 가는 전체적인 뼈대를 먼저 이해하고 시작해서, 다음번엔 에러 앞에서도 덜 당황하고 싶습니다.

## 5. 소감 — 발표 1분 원고

이번 프로젝트에서 UDT 서비스의 핵심인 거래 상세 화면을 담당하며, 에스크로 결제 시스템이 사용자에게 어떻게 신뢰를 줄 수 있는지 고민하고 구현해 볼 수 있어 매우 뜻깊은 시간이었습니다. 기술적인 어려움도 많았지만 팀원들과의 활발한 소통 덕분에 성공적으로 시연 화면을 완성할 수 있었고, 협업의 진짜 가치를 배웠습니다. 앞으로도 끊임없이 질문하고 성장하고 싶습니다. 감사합니다.
