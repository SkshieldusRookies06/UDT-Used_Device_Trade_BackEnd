## 3. 배운 것 — 협업

- 공용 영역을 담당할수록 내 기능뿐 아니라 다른 담당자의 화면까지 함께 확인해야 했다.
    - FE-A가 담당한 `Layout`, `Header`, 공용 컴포넌트, `authStore`·`wishStore`는 FE-B·FE-C의 화면에서도 공통으로 사용되기 때문에 작은 수정도 다른 화면의 동작에 영향을 줄 수 있었다.
    - 찜 상태는 상세 화면에서 바뀌고 목록 카드와 마이페이지에서도 보여야 하는 상태였는데, 티켓에도 `wishStore` 수정은 FE-A에게 요청하도록 되어 있었다. 그래서 상세 화면 코드는 건드리지 않고 공용 `ProductCard`·`Layout`·`authStore` 쪽에서 상태 동기화와 복원, 초기화를 처리했다.
    - 이를 통해 공용 코드는 단순히 재사용하기 위한 코드가 아니라 여러 담당자의 기능을 연결하는 부분이라는 것을 배웠다.

- 다른 담당자가 만든 화면을 수정할 때는 정해진 범위 안에서만 고쳐야 했다.
    - T-020은 다른 담당자의 `pages/`를 수정할 수 있는 티켓이어서 `*.module.css`와 `tokens.css`를 중심으로 수정했고, 컴포넌트 구조(JSX)는 바꾸지 않고 색·간격은 토큰 변수를 사용하는 제약이 있었다.
    - 실제로 7개 화면의 반응형 수정은 CSS와 토큰을 중심으로 처리했고, 구조를 바꾸지 않고 해결하는 방법을 먼저 찾게 되었다.
    - 여러 사람이 만든 화면을 통합할 때는 각 담당자의 구조를 존중하면서 공통 기준을 맞추는 것이 중요하다는 것을 배웠다.

- PR을 main에 합치는 것 역시 하나의 협업 과정이라는 것을 경험했다.
    - 팀원들은 각자 브랜치에서 작업해 PR을 올리고, 나는 프론트 PR을 main에 머지하는 역할을 맡아 프로젝트 기간 동안 17개의 merge commit을 처리했다.
    - 내 PR에서도 수용 기준 체크와 build·gate 출력을 남기고, 찜 상태 수정 PR에서는 확인한 항목과 확인하지 못한 항목(브라우저 화면 확인 미실시, 목 서버 한계로 실제 백엔드 재검증 필요)을 나눠 적었다.
    - 각 기능이 개별적으로 동작하는 것과 main에서 함께 동작하는 것은 다를 수 있기 때문에, PR에 무엇을 확인했고 무엇이 남았는지가 분명해야 머지 이후 확인할 부분도 정할 수 있다는 것을 배웠다.

## 4. 아쉬운 것 · 다음에 다르게 할 것

- 이번 프로젝트에서는 공용 UI와 인증 영역을 맡아 다른 팀원의 기능과 연결되는 부분이 많았는데, 초반에 공용 컴포넌트와 상태 관리 방식에 대해 조금 더 구체적으로 정하고 공유했으면 후반의 수정 작업을 줄일 수 있었을 것 같다.
- 기능 구현을 우선하면서 반응형 작업을 마지막에 한꺼번에 진행했는데, 여러 사람이 만든 화면을 한 번에 수정하려다 보니 확인해야 할 범위가 생각보다 컸다.
- 다음에는 각 화면을 구현하는 단계부터 공통 breakpoint와 모바일 화면까지 같이 확인하면서 작업하고 싶다.
- 상세 화면의 찜과 목록 카드처럼 담당이 나뉜 화면 사이의 문제는 각자 화면만 봐서는 드러나지 않았기 때문에, 다음에는 프로젝트 중간에도 화면을 이어서 확인하는 통합 점검을 진행해보고 싶다.

## 5. 소감

저는 프론트엔드 FE-A를 맡아 공용 UI와 로그인·회원가입, 인증 처리, 공용 상태 관리와 반응형 작업을 담당했습니다.  
공용 영역을 담당하면서 제가 만든 코드가 다른 팀원들의 화면에도 직접 연결되는 경우가 많아, 한 화면의 기능만 구현하는 것보다 전체 서비스의 흐름을 함께 확인하는 것이 중요하다는 것을 배웠습니다.  
또 팀원들의 PR을 main에 머지하는 역할을 맡으면서 각자 만든 기능이 하나로 합쳐질 때 어떤 부분을 확인해야 하는지 고민하게 되었습니다.  
특히 상세 화면에서 바꾼 찜 상태가 목록 카드에 반영되지 않았던 문제를 고치면서, 화면마다 따로 보면 문제가 없어 보여도 공유하는 상태를 기준으로 보면 빠진 부분이 있을 수 있다는 것을 경험했습니다.  
이번 프로젝트를 통해 공용 컴포넌트와 전역 상태, 인증 같은 기능이 각 화면을 어떻게 연결하는지 이전보다 구체적으로 이해할 수 있었습니다.  
또 단순히 제 기능을 완성하는 것에서 끝나는 것이 아니라 팀원들의 코드가 하나의 서비스로 합쳐지는 과정까지 경험할 수 있어서 좋았습니다.
