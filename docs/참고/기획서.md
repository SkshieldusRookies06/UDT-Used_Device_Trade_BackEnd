## 1. 프로젝트 개요

### 1.1 한 줄 정의

중고 전자기기 거래에서 발생하는 **"돈을 보내고 물건을 받지 못하거나, 사진과 다른 물건을
받는"** 신뢰 문제를, 거래 상태 프로세스 자체로 해결하는 웹 서비스.

### 1.2 해결하려는 문제

개인 간 중고 거래는 판매자와 구매자가 서로를 검증할 방법이 없다. 기존 서비스는 상품을
**보여주는 것**에 집중하지만, 실제 분쟁은 **돈과 물건이 오가는 과정**에서 발생한다.

UDT는 상품 목록·검색보다 **거래가 어떤 상태를 거치는가**를 서비스의 중심에 둔다.

```
관리자 검수  →  가상 에스크로  →  구매확정 전 정산 보류  →  분쟁 시 관리자 개입
(허위 매물 차단)  (선결제)        (판매자에게 바로 안 감)    (증빙 기반 환불/확정)
```

### 1.3 목표 사용자

| 사용자 | 필요 |
|---|---|
| 판매자 | 검수를 통과한 상품이라는 신뢰 표시 · 확실한 대금 수령 |
| 구매자 | 물건을 확인하기 전까지 돈이 판매자에게 넘어가지 않는 안전장치 |
| 관리자 | 허위 매물 사전 차단 · 분쟁 발생 시 증빙 기반 판단 |

## 2. 범위 정의 및 우선순위

2주라는 기간과 7명이라는 인원을 고려해, **거래 신뢰 프로세스**에 범위를 집중했다.

### 2.1 포함 (P1 — 반드시 구현)

| 영역 | 기능 |
|---|---|
| 회원 | 회원가입 · 로그인(JWT) · 마이페이지 · 가상 잔액 |
| 상품 | 등록(이미지 다중 업로드) · 목록(검색·카테고리·페이징) · 상세 · 찜 |
| 검수 | 관리자 승인/반려 (등록 상품은 검수 통과 후 노출) |
| 거래 | 구매 요청(가상 결제) · 배송정보 등록 · 구매확정 · 정산 |
| 분쟁 | 증빙 파일 첨부 신고 · 관리자 강제 환불/확정 |
| 관리자 | Thymeleaf 서버 렌더링 화면 (검수 · 분쟁 처리) |

### 2.2 우선순위 P2 (상위 기능 완료 후)

거래 후기(Review) — 핵심 거래 흐름에 필수가 아니다.

### 2.3 제외 — 기간 대비 실현성 검토 결과

| 제외 항목 | 이유 |
|---|---|
| 실시간 채팅 | WebSocket 도입 비용이 2주 일정에서 회수되지 않는다 |
| 실제 PG 결제 | 가맹점 심사·정산 연동이 교육 프로젝트 범위를 벗어난다. **가상 잔액으로 동일한 상태 흐름을 구현**한다 |
| 소셜 로그인 | 자체 인증(JWT)만으로 인증·인가 요구를 충족한다 |
| 알림·이메일 발송 | 외부 서비스 의존이 생기고 시연에 필수가 아니다 |
| 배포 | 기능 완성도와 문서화를 우선했다. 재현성은 README 실행 절차로 확보한다 |
| 관리자 권한 세분화 | 역할 2종(MEMBER·ADMIN)으로 고정 |

### 2.4 외부 의존성

**없음.** 외부 API·크롤링을 사용하지 않는다. 모든 데이터는 초기 시드와 사용자 입력에서
나온다 — 키 발급·요금제·응답 지연이라는 일정 위험이 구조적으로 0이다.

## 3. 핵심 시나리오 (시연 경로)

```
① 판매자 로그인 → 상품 등록(사진 3장) → 상태 "검수대기"
② 관리자 로그인 → 검수 승인 → 상태 "판매중"으로 전환
③ 구매자 로그인 → 검색 → 상세 → 찜 → 구매하기 → 잔액 차감 · 상태 "거래중"
④ 판매자 → 송장번호 입력 → "배송중"
⑤ 구매자 → 분쟁 신고(증빙 사진 첨부) → "분쟁"
⑥ 관리자 → 증빙 다운로드 → 강제 환불 → 구매자 잔액 복구 · 상품 "판매중" 복귀
⑦ (정상 경로) 구매확정 → 판매자 잔액 증가 · 상품 "거래완료"
```

⑥과 ⑦이 이 서비스의 존재 이유다. **구매확정 전까지 대금은 판매자에게 가지 않는다.**
