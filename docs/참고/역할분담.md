## 1. 편성 — 조 2개 · seam 1개

```
┌─────────────── 백엔드 조 (4명) ───────────────┐        ┌────── 프론트 조 (3명) ──────┐
│  BE-A  도메인·Entity·공통 + 리포/게이트 (팀장) │        │  FE-A  공통 구조·인증 화면   │
│  BE-B  인증·Security → 관리자 SSR             │◀ API ▶│  FE-B  상품 3화면            │
│  BE-C  상품·업로드·검색·N+1                   │ seam   │  FE-C  마이페이지·거래 상세  │
│  BE-D  거래·분쟁 (TransactionService 오너)     │  1개   │                             │
└───────────────────────────────────────────────┘        └─────────────────────────────┘
```

**팀 층 seam은 API 하나다.** 조 내부(BE끼리·FE끼리)는 seam이 아니므로 구두 조율이 허용되고
계약 문서도 필요 없다. 게이트도 하나 — `node seams/check-api.mjs`.

### 인원 4:3의 근거
Thymeleaf 관리자 화면은 화면 목록상 프론트로 분류되지만 **실제 작업은 서버 쪽**이다
(SSR 템플릿 · 폼 처리 · Security 체인). 여기에 파일 업로드·N+1 튜닝처럼 서버에만 있는
작업을 더하면 작업량이 백엔드로 기운다. 4:3은 그 비중을 따른 것이다.

### 계약 협상 짝 (이 둘이 합의하면 계약이 확정된다)

| 프론트 | 백엔드 | 무엇에 대해 |
|---|---|---|
| FE-A | BE-B | 로그인·회원가입·토큰 만료 동작 |
| FE-B | BE-C | 상품 목록·상세·등록·찜·이미지 |
| FE-C | BE-D | 거래 상태별 액션·분쟁 신고·파일 |

**오너는 겹치지 않는다** — 한 사람이 seam 양쪽 오너면 계약을 혼자 바꾸게 되고, 그 순간
계약이 계약이 아니게 된다.

### 인계가 일어나는 곳 하나 — `repository/`

BE-A가 D1~D2에 Repository 골격(인터페이스 + 기본 메서드)을 만들고, **D2 저녁에 파일 단위로
넘긴다**. 그 뒤로는 Service 오너가 자기 Repository를 소유한다.

| 파일 | D1~D2 | D3~ |
|---|---|---|
| `ProductRepository` · `WishRepository` · `CategoryRepository` | BE-A | **BE-C** |
| `TransactionRepository` · `DisputeRepository` | BE-A | **BE-D** |
| `UserRepository` | BE-A | BE-A (인증은 BE-B가 소비만) |

**엔티티(`entity/`)는 인계하지 않는다** — 끝까지 BE-A 단독이다. 엔티티에 필드가 필요하면
직접 고치지 말고 BE-A에게 요청한다(`SPEC.md` §10 변경 규약).

### 공용 파일 명단 (수정은 작게 · 즉시 머지 · 선공지)

| 파일 | 오너 |
|---|---|
| `SPEC.md` · `seams/` · `mock/` · `CLAUDE.md` · `data.sql` · `pom.xml` (backend 리포) | BE-A |
| `config/CorsConfig` · `common/*` (backend 리포) | BE-A |
| `SecurityConfig` (backend 리포) | BE-B |
| `application.yml` · `application-local.yml` (backend 리포) | BE-A — **키 블록 단위로 추가만** 하고 남의 키는 고치지 않는다. BE-B는 `app.jwt.*`, BE-C는 `hibernate.default_batch_fetch_size` 한 줄 (선공지 후 커밋) |
| `src/App.jsx` · `routes.js` · `store/` · `styles/` · `components/` · `seams/gate.mjs` (frontend 리포) | FE-A |
| `src/api/client.js` (인스턴스·인터셉터) | FE-A — **여기만 FE-A 단독** |
| `src/api/auth.js` / `products.js` / `transactions.js` | 각각 **FE-A / FE-B / FE-C**. 파일이 갈려 있으니 충돌하지 않는다. **새 도메인이 필요하면 파일을 새로 만든다** — 남의 파일에 함수를 끼워 넣지 않는다 |
| `package.json` · `package-lock.json` | FE-A (의존성 추가는 **팀 채널 선공지 후 커밋**) |

**lock 파일 충돌은 손으로 병합하지 않는다** — main의 `package.json`을 받아 재생성한다.

## 3. 팀장(BE-A)이 관리자로만 소진되지 않게

관리 작업을 **팀 산출물로 인정한다** — 게이트·목 서버·리포 셋업·시드가 팀장의 산출물이고,
커밋 로그가 그 증빙이다. 그 위에 구현 몫(엔티티 8개 + 공통 예외)을 남긴다.

- **중재는 위임하지 않되 진단은 위임한다.** "누구 쪽 버그냐"는 `SPEC.md` §11이 기계적으로
  답하므로 팀장을 부를 일이 아니다. 팀장이 불려야 하는 것은 **계약 결함** 판정뿐이다.
- **결정은 안건으로 배포한다.** 이 문서와 `SPEC.md`의 `[초안 — D1 회의 안건]` 절은 확정이
  아니다. 회의에서 확정·수정한 뒤 태그를 떼고 ADR에 "회의에서 이렇게 정함"을 남긴다.
- **운영 규칙 자체도 안건이다.** 게이트를 돌린다 · 구두 합의를 무효로 한다 · 목만 쓴다 ·
  전면 재작성을 금지한다 — 이것도 한 사람이 정한 규칙이다. D1 회의에 "운영 규칙" 항목을
  따로 올려 **명시적 동의**를 받는다. 안 받으면 3일차에 "왜 네가 정한 대로 해야 하냐"가 나온다.

### 최소 채택 집합 (부담되면 나머지는 버려도 된다)

```
M1. 첫날 API 계약 + 목 서버        — 없으면 프론트 3명이 절반의 기간을 대기한다
M2. 게이트 1개 + "완료 = 게이트 출력" — 없으면 완료 판정이 산문으로 돌아간다
M3. D4 1차 통합                   — 없으면 마지막 주가 통합 지옥이 된다
M4. D9 저녁 기능 동결              — 시연에서 터지는 것은 항상 마지막에 들어온 기능이다
M5. 막힘 공개(양방향)              — 없으면 7명 중 조용히 우회하는 사람이 생긴다
```

먼저 버려도 되는 것: ADR 개수 · 와이어프레임 장수 · 스탠드업 정시성 · 보드 도구 · 기능 목록의 완전 매핑.

---

> **실제 작업 지시서는 각 리포의 `tasks/`에 있다.** 티켓마다 배경·목표·수용 기준·제약·
> 확인 명령 다섯 칸이 채워져 있고, 수용 기준은 전부 기계로 판정되는 형태다.

### 3.1 머지 거절 기준 (오너용 · BE-A·FE-A가 쓴다)

규칙은 **첫 거절**에서 생긴다. 아래 넷 중 하나면 이유를 말하지 말고 표를 가리킨다.

| 반려 | 판정 방법 | 되돌려 줄 말 (그대로 복사) |
|---|---|---|
| 한 화면(≈100줄)을 넘는다 | `git diff --stat` | "티켓을 둘로 쪼개서 다시 올려 주세요. 큰 diff는 리뷰가 안 됩니다" |
| 수정 허용 밖 파일을 건드렸다 | diff의 파일 목록 vs 티켓 `[제약]` | "`<파일>`은 `<오너>` 소유입니다. 그 부분만 빼고 다시 올려 주세요. 필요하면 오너에게 요청" |
| 게이트가 red | `node seams/check-api.mjs` / `npm run build` | "게이트 green 찍고 다시요" |
| 전면 재작성 (기존 줄이 대부분 사라짐) | diff에서 `-` 가 `+` 만큼 많다 | "원인만 고친 최소 diff로 다시 올려 주세요. 다시 짠 건 새 버그가 들어옵니다" |

> 에이전트에 리포를 통째로 넣고 받아 온 코드가 넷 중 셋에 걸린다. **거절은 사람을 거절하는 게 아니라 diff를 거절하는 것**이고,
> 첫 번째를 거절하면 두 번째부터는 아무도 안 들고 온다.

### 매일의 리듬

```
아침 스탠드업 3문장 (1인당 · 15분 캡 · 7명이면 1인 2분을 넘기지 않는다)
1) 어제 머지한 것 — 커밋·게이트 green/red로 (산문 진행률 "70% 됐어요" 금지)

```

**주말·공백은 버퍼로 두고 계획 진도에서 뺀다.**

### 스프린트로 부르면 (애자일 요구가 있을 때)
