2. **계약이 코드보다 먼저다.** API 모양을 먼저 정해야 프론트와 백엔드가 동시에 달린다.
3. **통합을 두 번 한다.** 마지막에 한 번 합치면 그게 통합이 아니라 재작성이 된다.
4. **마지막 2일은 새 기능을 안 만든다.** 시연에서 터지는 건 항상 마지막에 들어온 기능이다.

```bash
# 백엔드  (IntelliJ 실행 버튼 = spring-boot:run · IntelliJ 테스트 실행 = mvnw test — 어느 쪽이든 된다)
```

```
worklog/<내이름>/D0N.md
1) 머지: T-006 · a1b2c3d · check-api 9/9 ok
2) 열었음: T-007
3) 막힘: 없음
```

> **일지는 3줄을 넘기지 않는다.** 나중에 회고록과 기여 증빙이 여기서 자동으로 나온다.
> 안 쓰면 D9에 기억으로 써야 하고, 그러면 절반은 틀린다.

### 30분 규칙

**같은 문제로 30분 막히면 말한다.** 질문은 잘못이 아니라 팀 일정을 구하는 행위다.
오너는 30분 안에 답하거나 "언제 보겠다"를 답한다.

처음 하는 사람이 가장 많이 하는 실수가 **혼자 3시간 파는 것**이다.
그 3시간에 옆 사람은 같은 문제를 5분 만에 푼 적이 있다.

**오후 — 통합에서 나온 문제 해결**

여기서 터지는 것들은 정해져 있다. 당황하지 않는다.

| 첫 페이지가 빈 결과 | 한쪽이 1-base로 바꿈 | 양쪽 확인 |
| 필드가 없다 | 계약에 있는데 구현에 없다 | 백엔드 |

## 4. 일정이 밀리면 — 버리는 순서

**절대 안 버리는 것 5개** (§D1 운영 규칙과 같다)

```
계약 + 목 서버 · 게이트 · D4 통합 · D9 기능 동결 · 30분 규칙
```

**밀릴 때 이 순서로 버린다**

| 순서 | 버리는 것 | 잃는 것 |
|---|---|---|
| 1 | 후기(Review) 기능 | 원래 우선순위 P2다. 잃는 것 없음 |
| 2 | 반응형 태블릿(768) | 모바일 390과 데스크톱만 남긴다 |
| 3 | 상품 카테고리 필터 | 검색만 남긴다 |
| 4 | 찜 기능 | 화면에서 버튼을 숨긴다 |
| 5 | 분쟁 증빙 **여러 장** | 1장만 받는다 |
| 6 | 관리자 분쟁 화면의 강제 확정 | 강제 환불만 남긴다 |

**절대 버리면 안 되는 것:** 구매 → 배송 → 구매확정 흐름과 관리자 검수.
**이 둘이 이 서비스의 존재 이유**라서, 이게 빠지면 주제 자체가 성립하지 않는다.
