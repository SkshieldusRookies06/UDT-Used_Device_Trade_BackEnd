# T-019 — 상품 목록 N+1 해결

**담당:** BE-C · **브랜치:** `be-perf` · **예상:** D7 · **선행:** T-006 · T-008

## [배경]

`GET /api/products` 는 상품 12건을 조회하면서 각 상품의 **판매자·카테고리·이미지·찜 수**를
읽는다. 기본 설정에서는 상품 1건마다 추가 쿼리가 나간다.

```
대상: GET /api/products (상품 목록) — 1개 엔드포인트에 집중한다
to-one (seller · category)  → fetch join 또는 @EntityGraph
컬렉션 (images)             → hibernate.default_batch_fetch_size: 100
```

> **컬렉션에 `fetch join` + 페이징을 같이 쓰지 않는다.** 하이버네이트가 페이징을 메모리에서
> 처리해(`HHH90003004` 경고) 전체 행을 다 읽어 온다. 컬렉션은 batch size로 푼다.

`application-local.yml`에 `logging.level.org.hibernate.SQL: debug`가 이미 켜져 있다.
쿼리를 세려면 `show_sql`도 잠깐 켠다 — `spring.jpa.properties.hibernate.show_sql: true`.
**`default_batch_fetch_size`는 일부러 빼 뒀다** — 이 티켓이 넣을 줄이고, 미리 있으면 '개선 전'을 못 찍는다.

## [목표]

쿼리 수를 줄이고, **개선 전후를 눈에 보이는 증거로 남긴다.**

## [수용 기준]

- [ ] **개선 전 쿼리 로그 캡처** — `docs/images/n1-before.png`
      (`GET /api/products?size=12` 1회 호출 시 발생한 select 문 전부)
- [ ] 개선 적용 — to-one은 `fetch join`/`@EntityGraph` · 컬렉션은 batch size
- [ ] **개선 후 쿼리 로그 캡처** — `docs/images/n1-after.png`
- [ ] 쿼리 수를 세어 문서에 기록: `docs/02-Entity설계서.md` §8.1
      (`[D7] 쿼리 수: 개선 전 N건 → 개선 후 N건` 자리를 실제 숫자로)
- [ ] **응답 내용은 하나도 바뀌지 않았다** — `node seams/check-api.mjs` 전부 ok
- [ ] `HHH90003004` 경고가 로그에 없다

## 쿼리 수 세는 법

```bash
# IntelliJ ▶ UdtApplication 기동 → 콘솔 우클릭 → Clear All (직전 로그를 비운다)
# 터미널에서 1회 호출
curl -s "localhost:8080/api/products?page=0&size=12" > /dev/null
# 콘솔 전체 선택·복사 → run.log 로 저장 후
grep -c "^Hibernate:\|select" run.log
# (또는 콘솔 검색창에 "Hibernate:" 를 치면 건수가 우측에 뜬다)
```

## [제약]

- 수정 허용: `repository/ProductRepository.java` · `service/ProductService.java` ·
  `application.yml`의 **`jpa.properties.hibernate.default_batch_fetch_size` 한 줄만**
- **`application.yml`은 BE-A 소유 공용 파일이다** — BE-B의 `app.jwt.*` 블록을 건드리지 않는다.
  이 한 줄 때문에 충돌이 나면 main을 받아 그 줄만 다시 넣는다 (`역할분담.md` §2)
- **API 응답을 바꾸지 않는다** — 성능만 바꾼다
- 캡처는 **같은 조건**(같은 엔드포인트·같은 size)에서 전후를 찍는다

## [확인 명령]

```bash
node seams/check-api.mjs
grep -n "HHH90003004" run.log     # 무출력이 정상
```
