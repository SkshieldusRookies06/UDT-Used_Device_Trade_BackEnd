# T-022 — 거래 게이트 확장 · 테스트 보강 · 엣지 케이스

**담당:** BE-A (9/29 BE-D → BE-A 이관 — 인수 테스트와 같은 오너로) · **브랜치:** `be-transaction-hardening` · **예상:** D5~D6 (게이트 검사 3개는 **이미 들어감** — 9/27 팀장 반영. 남은 것은 테스트 보강) · **선행:** T-009 · T-021

## [배경]

게이트(`seams/check-api.mjs`)는 상품·인증·`/api/me` 10개 + **거래 3개(9/27 반영 완료)** = 13개다.
T-009가 머지된 뒤, 계약 표류를 D5 이후에도 기계가 잡도록 검사 3개를 추가하고, 상태 머신의 엣지를 테스트로 닫는다.
`seams/`는 BE-A 소유이므로 **검사 코드는 BE-A와 페어로 넣거나 diff로 넘긴다** — 게이트를 통과시키려고 게이트를 고치는 것과는 다르다.

## [목표]

거래 계약이 기계로 검증되고, 상태 머신의 경계가 전부 테스트로 증명된다.

## [수용 기준]

- [x] 게이트에 검사 3개 추가 → **13/13** (반영됨 — `seams/check-api.mjs` 하단 "거래 3종")
      - `POST /api/products/{id}/purchase` → 201 · `data.buyerId`·`data.sellerId`가 문자열
      - `GET /api/transactions/{id}` → `status`가 5종 enum 중 하나 · `amountKrw` 숫자
      - `PATCH /api/transactions/{id}/confirm` (PAID 상태에) → 409 `INVALID_TRANSACTION_STATUS`
- [x] 목 서버도 13/13 (목이 계약을 따르는지 같은 검사로)
- [x] 테스트 추가: 잔액 정확히 0 남는 구매 · 같은 사용자가 두 상품 연속 구매(`PurchaseEdgeCaseTest`) · 판매자가 자기 거래를 구매확정 시도(403 · `ConfirmApiTest`) ·
      `REFUNDED` 상품을 다시 구매(ON_SALE로 복귀했으므로 성공 · `RepurchaseAfterRefundTest`)
- [x] `approveInspection`·`rejectInspection`(`InspectionTest`) · `forceRefund`·`forceConfirm`(`ForceResolutionDisputeTest`) (BR-01·02·07·08) 테스트
- [x] 테스트 전체 통과(IntelliJ) (MariaDB 기동 상태)

## [제약]
