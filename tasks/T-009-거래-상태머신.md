# T-009 — 거래 상태 머신 (구매요청 · 송장 · 구매확정)

**담당:** BE-D · **브랜치:** `be-transaction` · **예상:** D1~D3 · **선행:** T-002 · T-003
**이 티켓이 이 서비스의 핵심이고, 발표에서 가장 큰 비중을 차지한다.**

## [배경]

`SPEC.md` §2.3 상태 머신 · §2.4 맞물리는 규칙이 정본이다.

```
Product      INSPECTING → ON_SALE → IN_TRADE → SOLD
Transaction  PAID → SHIPPING → CONFIRMED
                └──────────────┴──▶ DISPUTED → REFUNDED | CONFIRMED
```

**각 줄이 한 트랜잭션이다:**

| # | 행위 | 같이 바뀌는 것 (원자적) |
|---|---|---|
| BR-03 | 구매 요청 | Product `ON_SALE → IN_TRADE` · Transaction 생성 `PAID` · **buyer.balance −= price** |
| BR-04 | 송장 입력 | Transaction `PAID → SHIPPING` + courier·trackingNo |
| BR-05 | 구매 확정 | Transaction `→ CONFIRMED` · Product `→ SOLD` · **seller.balance += amount** |

> **BR-03과 BR-05 사이가 에스크로다.** 구매자 돈은 즉시 빠지지만 판매자에게는
> 구매확정 때 처음 들어간다.

계약 (`SPEC.md` §4.5~4.7):

```
POST  /api/products/{id}/purchase       201 · 409 PRODUCT_NOT_ON_SALE
                                        · 400 SELF_PURCHASE_NOT_ALLOWED
                                        · 400 INSUFFICIENT_BALANCE
PATCH /api/transactions/{id}/shipping   200 · 판매자만 · PAID 상태에서만
                                        body {courier, trackingNo(숫자 8~20자리)}
PATCH /api/transactions/{id}/confirm    200 · 구매자만 · SHIPPING 상태에서만
GET   /api/transactions/{id}            200 · 당사자만 · 403 TRANSACTION_FORBIDDEN
GET   /api/me/transactions?role=buyer|seller
```

**§2.5 — 상태 변경은 `TransactionService`에서만 한다.** 분쟁(T-010)과 관리자 화면(T-018)은
이 서비스의 메서드를 호출만 한다. 이 규칙이 없으면 상태 변경 코드가 세 군데로 흩어진다.

## [목표]

구매 → 배송 → 확정의 전체 흐름이 원자적으로 동작한다.

> **BR-01·BR-02(검수 승인/반려)도 이 티켓 범위다.** Product 상태를 바꾸는 코드가
> `TransactionService` 밖에 생기면 §2.5가 깨진다. 관리자 화면(T-018 · BE-B)은 이 둘을 호출만 한다.

## [수용 기준]

- [ ] `TransactionService`에 `purchase` · `registerShipping` · `confirm` — **모두 `@Transactional`**
- [ ] **구매 요청 후 상태 3개가 함께 바뀐다** — 아래 SQL로 확인

```sql
SELECT p.status product_status, t.status txn_status, u.balance_krw buyer_balance
FROM transactions t JOIN products p ON p.id = t.product_id JOIN users u ON u.id = t.buyer_id
WHERE t.id = <거래ID>;
-- 구매 직후: IN_TRADE / PAID  / 차감됨
-- 확정 직후: SOLD     / CONFIRMED · 판매자 잔액 증가
```

- [ ] 잔액 부족 계정(`buyer2@udt.test`, 30만원)으로 85만원 상품 구매 → **400 `INSUFFICIENT_BALANCE`**
      **그리고 아무 데이터도 바뀌지 않았다** (상품 여전히 ON_SALE · 거래 미생성)
- [ ] 본인 상품 구매 → 400 `SELF_PURCHASE_NOT_ALLOWED`
- [ ] 이미 거래중 상품 구매 → 409 `PRODUCT_NOT_ON_SALE`
- [ ] 판매자가 구매확정 시도 → 403 `TRANSACTION_FORBIDDEN`
- [ ] `PAID` 상태에서 구매확정 시도 → 409 `INVALID_TRANSACTION_STATUS`
- [ ] 송장번호 `abc` → 400 `VALIDATION_ERROR` + `fields[{name:"trackingNo"}]`
- [ ] 제3자가 거래 조회 → 403

## [제약]

- 수정 허용: `controller/TransactionController.java` · `service/TransactionService.java` ·
  `dto/Transaction*` · `repository/TransactionRepository.java`
- **`Product`·`User`의 상태·잔액을 다른 Service에서 바꾸지 않는다** (§2.5)
- 거래 금액은 **생성 시점 상품 가격을 복사**해 저장한다 (나중에 가격이 바뀌어도 불변)
- 롤백 확인을 위해 **예외는 `RuntimeException` 계열**로 던진다 (checked면 기본 롤백이 안 된다)

## [확인 명령]

```bash
# 잔액 부족 시나리오 — 실패 후 아무것도 안 바뀌었는지가 핵심
TOKEN2=$(curl -s -X POST localhost:8080/api/auth/login -H "Content-Type: application/json" \
  -d '{"email":"buyer2@udt.test","password":"Test1234!"}' | jq -r .data.accessToken)
curl -s -X POST localhost:8080/api/products/1/purchase -H "Authorization: Bearer $TOKEN2" | jq .code
mysql -u udt -pudt -P 3307 udt -e "SELECT status FROM products WHERE id=1;"   # ON_SALE 유지
```
