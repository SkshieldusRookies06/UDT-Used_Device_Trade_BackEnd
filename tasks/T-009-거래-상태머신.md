# T-009 — 거래 상태 머신 (구매요청 · 송장 · 구매확정)

**담당:** BE-D · **브랜치:** `be-transaction` · **예상:** D1~D3 · **선행:** T-002 (T-003은 이 티켓 **다음**이다)
**이 티켓이 이 서비스의 핵심이고, 발표에서 가장 큰 비중을 차지한다.**

## [배경]

`SPEC.md` §2.3 상태 머신 · §2.4 맞물리는 규칙이 정본이다.

```
Product      INSPECTING → ON_SALE → IN_TRADE → SOLD
Transaction  PAID → SHIPPING → CONFIRMED
                └──────────────┴──▶ DISPUTED → REFUNDED | CONFIRMED
```

**각 줄이 한 트랜잭션이다:**

| # | 행위 | 같이 바뀌는 것 (원자적) |
|---|---|---|
| BR-03 | 구매 요청 | Product `ON_SALE → IN_TRADE` · Transaction 생성 `PAID` · **buyer.balance −= price** |
| BR-04 | 송장 입력 | Transaction `PAID → SHIPPING` + courier·trackingNo |
| BR-05 | 구매 확정 | Transaction `→ CONFIRMED` · Product `→ SOLD` · **seller.balance += amount** |

> **BR-03과 BR-05 사이가 에스크로다.** 구매자 돈은 즉시 빠지지만 판매자에게는
> 구매확정 때 처음 들어간다.

계약 (`SPEC.md` §4.5~4.7):

```
POST  /api/products/{id}/purchase       201 · 409 PRODUCT_NOT_ON_SALE
                                        · 400 SELF_PURCHASE_NOT_ALLOWED
                                        · 400 INSUFFICIENT_BALANCE
PATCH /api/transactions/{id}/shipping   200 · 판매자만 · PAID 상태에서만
                                        body {courier, trackingNo(숫자 8~20자리)}
PATCH /api/transactions/{id}/confirm    200 · 구매자만 · SHIPPING 상태에서만
GET   /api/transactions/{id}            200 · 당사자만 · 403 TRANSACTION_FORBIDDEN
GET   /api/me/transactions?role=buyer|seller   ← 목록 조회는 BE-A T-021. 여기선 TransactionResponse DTO만 확정
```

**§2.5 — 상태 변경은 `TransactionService`에서만 한다.** 분쟁(T-010)과 관리자 화면(T-018)은
이 서비스의 메서드를 호출만 한다. 이 규칙이 없으면 상태 변경 코드가 세 군데로 흩어진다.

## [목표]

구매 → 배송 → 확정의 전체 흐름이 원자적으로 동작한다.

> **BR-06의 전이 부분도 이 티켓이다** — `markDisputed(buyerId, txId)`: 당사자·상태(PAID|SHIPPING) 검사 후 `DISPUTED`로.
> Dispute 엔티티 생성·파일 저장은 BE-A의 T-010이 하고, 이 메서드를 같은 트랜잭션 안에서 호출한다(§2.5).

> **BR-01·BR-02(검수 승인/반려)도 이 티켓 범위다.** Product 상태를 바꾸는 코드가
> `TransactionService` 밖에 생기면 §2.5가 깨진다. 관리자 화면(T-018 · BE-B)은 이 둘을 호출만 한다.

## [수용 기준]

- [ ] `TransactionService`에 `purchase` · `registerShipping` · `confirm` — **모두 `@Transactional`**
- [ ] **구매 요청 후 상태 3개가 함께 바뀐다** — 아래 SQL로 확인

```sql
SELECT p.status product_status, t.status txn_status, u.balance_krw buyer_balance
FROM transactions t JOIN products p ON p.id = t.product_id JOIN users u ON u.id = t.buyer_id
WHERE t.id = <거래ID>;
-- 구매 직후: IN_TRADE / PAID  / 차감됨
-- 확정 직후: SOLD     / CONFIRMED · 판매자 잔액 증가
```

- [ ] 잔액 부족 계정(`buyer2@udt.test`, 30만원)으로 85만원 상품 구매 → **400 `INSUFFICIENT_BALANCE`**
      **그리고 아무 데이터도 바뀌지 않았다** (상품 여전히 ON_SALE · 거래 미생성)

- [ ] `[9/27 개정]` `PATCH` 매핑 · 공통 봉투 · `GET /api/transactions/{id}`(당사자 · `dispute` 키) · `/api/admin/**` 없음 · `buyerId`는 `CurrentUser.id()` — 아래 개정 표

## [제약]

- 수정 허용: `controller/TransactionController.java` · `service/TransactionService.java` ·
  `dto/Transaction*` · `repository/TransactionRepository.java`
- **`Product`·`User`의 상태·잔액을 다른 Service에서 바꾸지 않는다** (§2.5)
- 거래 금액은 **생성 시점 상품 가격을 복사**해 저장한다 (나중에 가격이 바뀌어도 불변)
- 롤백 확인을 위해 **예외는 `RuntimeException` 계열**로 던진다 (checked면 기본 롤백이 안 된다)

> **머지 조건 하나 더 — BE-A 리뷰 필수.** 이 티켓은 프로젝트에서 가장 위험한 30줄(동시성)을 담고 있다.
> `purchase()`의 조건부 UPDATE와 `updated == 0` 분기, 잔액 차감 순서를 BE-A가 diff로 읽고 승인해야 머지한다.

## [9/27 개정] 바뀐 것과 이유 — 팀장 전수 검증(`docs/참고/검증-0927.md`) 반영

`be-transaction` 브랜치 코드를 SPEC과 대조한 결과다. **문서(이 티켓·SPEC)와 테스트는 main에 들어갔고, 코드는 BE-D가 고친다.** 완료 판정은 위 테스트 3종 green.

| # | 있었던 것 | 계약 | 결과 | 어떻게 고치나 |
|---|---|---|---|---|
| 1 | `ProductRepository.transition()`이 `@Modifying(clearAutomatically = true)` | §2.4 BR-03 원자성 | 벌크 UPDATE 뒤 컨텍스트가 비워져 `buyer.withdraw()`가 **DB에 안 들어간다 → 구매해도 잔액이 안 빠진다.** Mockito 테스트는 못 잡음. (이 티켓 5절 예시 코드가 그 옵션을 권장했던 것이 원인 — 예시도 고쳤다) | `clearAutomatically` 제거(BE-C 승인 · 한 줄) + `transition()` 성공 직후 `product.changeStatus(IN_TRADE)`로 메모리도 맞춤 |
| 2 | 송장·확정이 `@PostMapping` | §4.6·§4.7 `PATCH` (프론트도 PATCH) | 통합 시 405(Advice가 500으로 감쌈) | `@PatchMapping` |
| 3 | 응답이 `TransactionResponse` 날것 | §0 공통 봉투 | 프론트 인터셉터 `res.data.data` → undefined | `ApiResponse.of(...)` · purchase는 201 유지 |
| 4 | `/api/admin/transactions/{id}/force-refund`·`force-confirm` | §2.5·§3.2·§8 B5 — 관리자 처리는 REST로 열지 않는다 | `/api/**` 체인은 역할을 안 봐서 **일반 회원이 강제 환불 가능** | 두 메서드 삭제. T-018(BE-B) 관리자 화면이 `forceRefund/forceConfirm`을 직접 호출 |
| 5 | `GET /api/transactions/{id}` 없음 | §4.9 당사자만 · `dispute` 객체 또는 null | FE-C 거래 상세 첫 호출 404 | `getDetail(requesterId, txId)` 추가 → 제3자 403 |
| 6 | `@RequestParam buyerId`·`sellerId` | §8 B6 | 아무 id나 넣어 남의 거래 조작 | 전부 `CurrentUser.id()`(공용 헬퍼 · main에 있음). `RequestParam` import 제거 |
| 7 | `ShippingRequest.trackingNo` `@NotBlank`뿐 | §4.7 숫자 8~20자 | `abc`가 통과 | `@Pattern(regexp = "\\d{8,20}")` |
| 8 | `TransactionResponse`에 `productTitle`·`buyerNickname`·`sellerNickname` 없음 | §4.5 예시 필드 | 화면에 상품명·닉네임 못 그림 | 세 필드 추가 · `from(tx, dispute)` 오버로드 · `DisputeResponse` record 신설(§4.8 모양 · T-010도 씀) |
| 9 | `forceRefund/forceConfirm`이 분쟁을 안 닫음 | §2.4 BR-07·08 네 번째 줄 | 환불됐는데 분쟁 OPEN | `disputeRepository.findByTransactionId()`(BE-A가 추가함)로 찾아 `dispute.resolve(memo, now)` — 같은 트랜잭션 |
| 10 | `TransactionRepository.findByProductId`가 `Optional` | §2.4 환불 후 재구매 → 상품당 거래 다건 | 2건이면 예외 | `List<Transaction>` |
