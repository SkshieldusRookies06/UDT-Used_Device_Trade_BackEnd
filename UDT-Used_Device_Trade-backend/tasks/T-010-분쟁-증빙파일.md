# T-010 — 분쟁 접수 · 증빙 업로드/다운로드

**담당:** BE-A · **브랜치:** `be-dispute` · **예상:** D5~D6 · **선행:** T-009(BE-D의 `markDisputed` 시그니처) · T-007(`FileStorageService`)

## [배경]

계약 (`SPEC.md` §4.8):

```
POST /api/transactions/{id}/disputes   (multipart)
  파트: dispute (JSON {reason} 10~500자) + files (0~3개 · jpg/png/pdf · 각 5MB)
  전제 상태: PAID 또는 SHIPPING · 구매자 본인만
  성공 201 · data = {id, transactionId, status, reason, files:[{id, originalName}], createdAt}
  에러: 409 DISPUTE_ALREADY_EXISTS · 409 INVALID_TRANSACTION_STATUS · 403 · 400

GET /api/disputes/{id}/files/{fileId}
  응답: 파일 바이트 + Content-Disposition: attachment; filename="..."
  권한: 거래 당사자 또는 ADMIN · 403 ACCESS_DENIED
```

업무 규칙 BR-D001·D002 — 거래당 분쟁은 한 번만, `uk_disputes_transaction`이 DB 방어선.

**다운로드가 이 프로젝트의 파일 다운로드 기능이다.** 관리자가 증빙을 내려받아 판단하는
흐름이 서비스의 본질이라 억지가 없다.

## [목표]

분쟁 접수와 증빙 파일 다운로드가 동작하고, 권한 밖 접근이 막힌다.

## [수용 기준]

- [ ] 분쟁 접수 → 201 · Transaction 상태가 **`DISPUTED`**로 바뀐다
      (**`TransactionService.markDisputed(buyerId, txId)`를 호출해서** — §2.5. 전이는 BE-D 것, Dispute 생성은 내 것.
      `DisputeService.open()`이 `@Transactional`이라 둘이 한 트랜잭션이다)
- [ ] `GET /admin/disputes/{id}/files/{fileId}` (세션 인증) 도 같은 저장·권한 코드로 동작한다 — BE-B의 관리자 화면이 링크한다
- [ ] 같은 거래에 재접수 → 409 `DISPUTE_ALREADY_EXISTS`
- [ ] `CONFIRMED` 상태 거래에 접수 → 409 `INVALID_TRANSACTION_STATUS`
- [ ] 판매자가 접수 시도 → 403 `TRANSACTION_FORBIDDEN`
- [ ] 사유 5자 → 400 `VALIDATION_ERROR` + `fields`
- [ ] **다운로드 응답에 `Content-Disposition: attachment; filename=` 헤더가 있다**
- [ ] 한글 파일명이 깨지지 않는다 (`filename*=UTF-8''...` 인코딩)
- [ ] 제3자가 다운로드 시도 → 403 `ACCESS_DENIED`

## [제약]

- 수정 허용: `controller/DisputeController.java` · `service/DisputeService.java` ·
  `dto/Dispute*` · `repository/Dispute*` · `admin/AdminDisputeFileController.java`(다운로드 1개 매핑만)
- **거래 상태를 직접 바꾸지 않는다** — `TransactionService`를 호출한다 (§2.5)
- 파일 저장·검증 로직은 T-007의 `FileStorageService`를 재사용한다 (중복 구현 금지)

## [확인 명령]

```bash
curl -sI "localhost:8080/api/disputes/1/files/1" -H "Authorization: Bearer $TOKEN" \
  | grep -i content-disposition
```
