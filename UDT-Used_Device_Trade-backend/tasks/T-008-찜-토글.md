# T-008 — 찜 추가/해제 · 내 목록

**담당:** BE-C · **브랜치:** `be-wish` · **예상:** D5 · **선행:** T-005 · T-006

## [배경]

계약 (`SPEC.md` §4.9):

```
POST   /api/products/{id}/wishes  201  data = {productId, wished:true,  wishCount}
                                  409 WISH_ALREADY_EXISTS
DELETE /api/products/{id}/wishes  200  data = {productId, wished:false, wishCount}
                                  404 WISH_NOT_FOUND
GET    /api/me/wishes             200  상품 목록 형식 {content[], page{}}
```

업무 규칙 BR-W001 — 같은 회원이 같은 상품을 두 번 찜할 수 없다.
**DB 제약 `uk_wishes_user_product`가 최후의 방어선**이고, Service에서도 먼저 확인한다.

## [목표]

찜 토글이 동작하고 중복이 DB 레벨에서도 막힌다.

> `GET /api/me/wishes`·`/api/me/products`는 **BE-A의 T-021**이 만든다. 이 티켓은 찜 토글(POST/DELETE)만.
> `WishRepository`에 `findByUserId(Pageable)` 같은 조회 메서드가 필요하면 BE-A가 T-021에서 넣는다.

## [수용 기준]

- [ ] 찜 추가 → 201 · `wished: true` · `wishCount` 증가
- [ ] 같은 상품 재찜 → **409 `WISH_ALREADY_EXISTS`** (500이 아니라)
- [ ] 찜 해제 → 200 · `wished: false` · `wishCount` 감소
- [ ] 찜하지 않은 상품 해제 → 404 `WISH_NOT_FOUND`
- [ ] 비로그인 → 401
- [ ] `GET /api/products/{id}` 의 `wished` 가 로그인 사용자 기준으로 바뀐다
      (비로그인이면 `false`)

## [제약]

- 수정 허용: `controller/WishController.java` · `service/WishService.java` ·
  `repository/WishRepository.java` · `dto/Wish*`
- 중복 검사를 **애플리케이션에서만** 하지 않는다 — DB 제약도 함께 살아 있어야 한다
- `wishCount`는 매번 세지 말고 조회 시 집계 (N+1 주의 — T-019와 연결)

## [확인 명령]

```bash
curl -s -X POST localhost:8080/api/products/1/wishes -H "Authorization: Bearer $TOKEN" | jq
curl -s -X POST localhost:8080/api/products/1/wishes -H "Authorization: Bearer $TOKEN" | jq .code
# → "WISH_ALREADY_EXISTS"
```
