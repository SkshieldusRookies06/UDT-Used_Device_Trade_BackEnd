# T-023 — 파일 저장·검증·서빙 (`FileStorageService` + 이미지 엔드포인트)

**담당:** BE-A · **브랜치:** `be-file` · **예상:** D3 (T-021과 같은 날 · 합쳐서 하루) · **선행:** T-002

## [배경]

파일을 다루는 곳이 둘이다 — 상품 이미지(T-007 · BE-C)와 분쟁 증빙(T-010 · BE-A). **저장·검증·이름 짓기·바이트 서빙은 한 벌**이어야 하고,
이 프로젝트에서 보안상 가장 새기 쉬운 자리(경로 조작 · 확장자 위장 · 남의 파일 열람)라 **경험 있는 사람이 한 번에 만든다.**
BE-C는 상품 등록에서 이걸 호출만 하고, 파일 문제는 전부 이 티켓으로 온다.

```
FileStorageService  (service/)
  store(MultipartFile, String subdir) → StoredFile{storedName, originalName, sizeBytes}
    - 확장자 화이트리스트: jpg jpeg png webp (+ 분쟁용 pdf 는 subdir 별 허용 목록)
    - 실제 내용 검사: 확장자만 믿지 않는다 — 매직 바이트 또는 ImageIO로 이미지 여부 확인
    - 용량 상한 5MB → FILE_TOO_LARGE · 형식 → FILE_TYPE_NOT_ALLOWED · 저장 실패 → FILE_STORAGE_ERROR
    - 저장 이름은 UUID + 확장자. 원본 이름은 DB에만
    - 저장 경로 = app.upload-dir / subdir / storedName. 경로에 원본 이름·".." 이 절대 안 들어간다
  load(String subdir, String storedName) → Resource
  contentType(storedName) → image/jpeg 등

GET /api/products/{id}/images/{imageId}   → 바이트 · Content-Type: image/* · 비로그인 허용 (permitAll 이미 있음)
```

## [목표]

파일 저장과 서빙이 한 곳에서 안전하게 되고, 상품·분쟁 둘 다 이걸 쓴다.

## [수용 기준]

- [ ] `.txt`를 `.jpg`로 이름만 바꿔 올리면 → 400 `FILE_TYPE_NOT_ALLOWED` (내용 검사)
- [ ] 6MB → 400 `FILE_TOO_LARGE`
- [ ] 원본 파일명이 `../../x.jpg` 여도 `uploads/` 밖에 아무것도 생기지 않는다
- [ ] 저장된 파일명이 UUID 형태 · 원본 이름은 `original_name` 컬럼에만
- [ ] `GET /api/products/{id}/images/{imageId}` → 200 · `Content-Type: image/jpeg|png|webp` · 없는 id → 404 `PRODUCT_NOT_FOUND`
- [ ] 다른 상품의 imageId를 넣으면 404 (상품-이미지 소속 검사)
- [ ] `uploads/` 가 없으면 기동 시 만든다 · 커밋되지 않는다
- [ ] BE-C가 `ProductService.create()`에서 `fileStorageService.store(file, "products")` 한 줄로 쓸 수 있다 (D3 저녁 공지)

## [제약]

- 수정 허용: `service/FileStorageService.java`(신규) · `controller/ProductImageController.java`(신규 · 이미지 GET 하나만) · `dto/StoredFile`
- **`ProductController`·`ProductService`는 건드리지 않는다** — 그건 BE-C(T-007)가 연결한다
- 응답 `Content-Disposition`은 이미지엔 안 붙인다(인라인 표시) · 증빙(T-010)엔 붙인다
